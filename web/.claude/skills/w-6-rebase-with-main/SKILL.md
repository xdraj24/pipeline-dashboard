# Rebase Branch onto Latest Main

Bring a branch fully up to date with `main`: fetch the latest `origin/main`, rebase onto it, and
resolve any conflicts so the branch's own functionality stays intact and nothing `main` added in
the meantime gets silently broken.

Host-specific mechanics (arguments, invoking other skills, delegation, asking the developer):
`.claude/skills/_shared/host-runtime.md`.

Argument: `$ARGUMENTS` — optional. A branch name (exact or partial). If omitted, use the
**current** branch.

Every question for the developer in this skill goes through
`.claude/skills/_shared/slack-escalation.md`.

## 1. Resolve the target branch

- **Argument given**: resolve it with the "With an argument" rules in
  `.claude/skills/_shared/find-branch.md`, apply its "Before switching branches" guard, then
  `git checkout <branch-name>` if it isn't already current.
- **No argument**: use whatever branch is currently checked out. If the current/resolved branch
  is `main` itself, tell the user there's nothing to rebase and stop.

## 2. Check the working tree

- `git status` — if there are uncommitted changes on this branch, stop and ask the user to commit
  or stash them first (`git stash push -u`); rebasing on top of a dirty tree risks losing work or
  producing confusing conflicts.

## 3. Fetch latest main

- `git fetch origin main`.

## 4. Rebase

- `git rebase origin/main`.
- **If it rebases cleanly**, go to step 5.
- **If there are conflicts**, resolve them file by file:
  - Read enough surrounding context on both sides to understand what each side was trying to do
    — this branch's change, and whatever landed on `main` since it diverged.
  - Preserve the **intent of both sides**: the branch's new functionality must survive the
    rebase intact, and it must not silently undo or break whatever `main` changed. Where the two
    changes genuinely overlap, merge the logic so both behaviors hold — don't just concatenate or
    delete one side.
  - Never resolve a conflict by blindly picking "ours" or "theirs" for logic-bearing code. Only
    take that shortcut for genuinely mechanical conflicts (import ordering, lockfiles,
    autogenerated files like `frontend/types/GraphqlSchema.ts` — regenerate those with `pnpm
    codegen` instead of hand-resolving).
  - After resolving each file: `git add <file>`. Once a step's conflicts are all resolved:
    `git rebase --continue`. Repeat until the rebase finishes.
  - **If a conflict involves business logic you're not confident about** — the two sides changed
    the same behavior in incompatible ways, or you can't tell which side should win — **stop**,
    run `git rebase --abort` to restore the pre-rebase state, show the user the conflicting hunks
    from both sides, and ask them how to resolve it. Do not guess on logic-bearing conflicts.
  - **If the rebase is clearly spiraling** (repeated conflicts in the same file across multiple
    commits, or conflicts you resolve that keep reappearing), `git rebase --abort` and ask the
    user for help rather than pushing through.

## 5. Verify nothing broke

A rebase can change behavior even without conflicts (surrounding context shifted, a dependency
changed on `main`). Re-run the checks for whatever the branch touches as
`.claude/skills/_shared/run-checks.md` describes.

- If Biome/RuboCop modified files, stage them and amend the relevant commit(s)
  (`git commit --amend --no-edit` if it's the tip commit; otherwise fold via
  `git commit --fixup` + `git rebase --autosquash origin/main` rather than hand-editing history
  further back).
- **If a test fails and you can't confidently fix it** without touching logic beyond what the
  rebase itself required, stop: show the user the failure and ask for help rather than guessing
  at a fix under a rebase's time pressure.

## 6. Report back

Summarize: how many commits were replayed, which files had conflicts and a one-line description
of how each was resolved, and the result of the post-rebase checks. Note that if the branch was
already pushed, its remote history has now diverged — a subsequent push needs
`--force-with-lease` (`/w-4-publish` already does this).
